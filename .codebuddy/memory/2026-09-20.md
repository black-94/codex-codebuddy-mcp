## codex-codebuddy-mcp 打包 / 本地安装 / docker ACP 联通

- 打包：`uv build`（hatchling backend）→ `dist/codex_codebuddy_mcp-0.1.0-py3-none-any.whl` + `.tar.gz`。
- 本地安装：`uv tool install --force dist/*.whl`，入口 `~/.local/bin/codex-codebuddy-mcp`（isolated env 在 `~/.local/share/uv/tools/codex-codebuddy-mcp`）。
- 用 `docker` 充当 ACP 承载进程的技巧：`create_codebuddy_session` 的 `codebuddy_command="docker"`，
  `codebuddy_args=["run","--rm","-i","--network=host","-v",<auth>:<target>,"-v",<workdir>:<workdir>,"-w",<workdir>,"agent-harness:2","codebuddy"]`，
  桥接会续接 `--model <id> --permission-mode auto --acp --acp-transport stdio`，即最终在容器里跑 codebuddy ACP。
  注意 `--model/--permission-mode/--acp` 由桥接管理，不能写进 `codebuddy_args`。
- 容器内 codebuddy 登录：镜像本身未登录（`_codebuddy.ai/getUserInfo` 返回 `{}`）。
  宿主机凭证导出到 `/srv/agent/auth/codebuddy/codebuddy1`，挂到容器 `/home/master/.local/share/CodeBuddyExtension` 后即已登录。
  只挂 `~/.codebuddy` 的 settings/local_storage/blobs 快照无效（凭证不在那里）。
- 容器内 codebuddy 2.155.0 可用模型（`--model` 取值）：hy3, glm-5.2, glm-5.1, glm-5.0, glm-5.0-turbo, glm-5v-turbo,
  glm-4.7, minimax-m3, minimax-m2.7, kimi-k3-1, kimi-k2.7, kimi-k2.6, kimi-k2.5, deepseek-v4-pro,
  deepseek-v4-flash, deepseek-v3-2-volc。
- 端到端验证：`uv run examples/docker_codebuddy_hi.py hi` → `status=completed`，`text="Hi! How can I help you today?"`
  （model glm-5.2，`docker run --rm` 容器退出后自动回收）。

## codex 能否走 ACP（结论：不能原生）

- `agent-harness:3` 内是 codex-cli 0.155.1，**没有 ACP**：`codex --help` 无 `acp` 子命令、无 `--acp/--acp-transport`；
  `codex features list` 全量特性中无 acp；包内 grep `acp-transport` 无命中。
- codex 对外只有自家协议：`codex app-server`（JSON-RPC，`--listen stdio://|unix://|ws://|off`，支持
  `generate-ts` / `generate-json-schema`）与 `codex app-server proxy`；`codex mcp` 只是管理外部 MCP server。
- 要 ACP 必须加适配器：`@agentclientprotocol/codex-acp`（ACP 官方组织，1.12.0 / 2026-09-15，内置 `@openai/codex` 依赖，
  可用 `CODEX_PATH` 换 binary；认证支持 ChatGPT 登录 / `CODEX_API_KEY` / `OPENAI_API_KEY`），
  或 `@zed-industries/codex-acp` 0.16.0。
- 与本桥接的冲突：桥接硬编码追加 `--model/--permission-mode/--acp/--acp-transport stdio`，适配器不认这些参数；
  绕法是让容器命令变成 `bash -c 'exec codex-acp'`，使追加参数落成 shell 位置参数被吞掉，模型改由
  `~/.codex/config.toml` 或 `-c model=...` 指定。codex0/config.toml 已有 `[projects."/workspace"] trust_level="trusted"`。

## agy_acp_server（Google Antigravity ACP server）

- 位置：`/opt/agy-acp-server/agy_acp_server.par`（1.88GB ELF，Python+absl 打包）软链 `/usr/local/bin/agy_acp_server`；
  同目录 `localharness_external`（静态 ELF）。agent-harness:2/3 都有，版本 `AGY_ACP_SERVER_VERSION=1.1.1`。
- **启动坑**：直接跑会 `Check failed: LookupGIDByGroupName(groupname, &new_gid) Group nobody not found`
  （Ubuntu 24.04 只有 `nogroup`，没有 `nobody` 组）。绕过办法：用一份补了 `nobody:x:65533:` 的 /etc/group
  挂进容器（`-v /tmp/group.probe:/etc/group`）；或在镜像里 `groupadd nobody`。
- 默认即 stdio ACP server；自有 flag 只有 `--debug` / `--notices`（其余是 absl），
  所以桥接硬编码追加的 `--model/--permission-mode/--acp/--acp-transport` 必须用
  `bash -c 'exec agy_acp_server'` 让它变成 shell 位置参数被吞掉。
- `initialize` → `agentInfo={name: antigravity-acp, title: Google Antigravity, version: agy_acp_server_1.1.1}`，
  `authMethods`: `oauth-personal` / `oauth-business` / `gemini-api-key` / `agent-platform`；
  能力含 loadSession、image/audio/embeddedContext、mcp http/sse、session list/resume、auth.logout。
- **鉴权是硬门槛**：未鉴权时 `session/new` 返回 `-32000 Authentication required`，提示两条路：
  (1) 调 `authenticate`；(2) 在 `/home/master/.gemini/antigravity-acp/settings.json` 写 `auth.type`。
  注意 `_codebuddy.ai/getUserInfo` 对它返回 `result: null`（不是 -32601），
  所以桥接 `_authenticate_if_required` 永远判定"未登录" ⇒ **必须显式传 `auth_method_id`**，否则永远建不了 session。
- **人工鉴权**：`authenticate {methodId: "oauth-personal"}` → stderr 打印
  `Open the following link to authenticate the ACP server: https://accounts.google.com/o/oauth2/v2/auth?...`
  是 **loopback OAuth + PKCE**，`redirect_uri=http://127.0.0.1:<随机端口>/`。
  因此容器必须 `--network=host`（已验证 `ss -ltn` 能看到宿主机 127.0.0.1:<port> LISTEN），
  用宿主机浏览器打开链接完成同意，回调打到该端口后 authenticate 才返回；
  `authenticate` 会一直阻塞，`startup_timeout_seconds` 要给足（如 900），否则被超时打断。
- `gemini-api-key` 方式：`authenticate` 返回 `-32602 The GEMINI_API_KEY environment variable must be set...`
  ⇒ 需要在**启动 ACP server 的环境**里有 `GEMINI_API_KEY`，走 docker 时要 `docker run -e GEMINI_API_KEY`
  （配合桥接 `env={"GEMINI_API_KEY": ...}` 让 docker 客户端进程持有该变量再 `-e` 透传）。
- 持久化目录：`/home/master/.gemini`（宿主机侧用 `/srv/agent/auth/agy/acp0`）；未登录前不会写任何文件。

### agy 实测最终结论

- 启动修复（二选一）：镜像 build 时 `groupadd -r nobody`，或运行时挂一份补了 `nobody:x:65533:` 的 /etc/group。
  实测该 check 只是启动门槛，进程**不会**真的切到 nobody（落盘文件仍属 master uid 1001）。
- 还必须设 `ANTIGRAVITY_HARNESS_PATH=/opt/agy-acp-server/localharness_external`，否则 session/new 报
  `-32603 Could not find default localharness binary`（镜像只把 agy_acp_server 软链进 PATH，漏了 localharness_external）。
- 人工鉴权实测：`authenticate(oauth-personal)` → stderr 打印 Google OAuth 链接（loopback + PKCE），
  本机浏览器完成同意后 authenticate 返回 `{}`；登录态落在 `<挂载的 .gemini>/antigravity-acp/`
  的 `settings.json`（自动写 `auth.type=oauth-personal`）与 `acp_token.json`（refresh_token/project_id/client_id...）。
  之后再次 authenticate 约 6s 返回、**不再弹 URL**，所以 900s 的 startup 超时只在首次登录需要。
- 模型：`session/new` 返回 `configOptions[id="model"].currentValue` + `models.availableModels`，共 11 个：
  gemini-3.8-flash-{high,medium,low}、gemini-3.7-flash-{high,medium,low}、gemini-3.6-flash-{high,medium,low}、
  gemini-pro-agent(Gemini 3.1 Pro High)、gemini-3.1-pro-low；默认 `gemini-3.7-flash-high`。
  另 modes: default / auto_edit / yolo。
  **切换模型必须用 `session/set_config_option {configId:"model", value:<modelId>}`**（实测切到
  gemini-3.8-flash-medium 后模型自报 "Gemini 3.8 Flash"）。`session/set_model` 返回 `{}` 无回执；
  settings.json 顶层 `model` 字段被忽略。
- 通过本 MCP 桥接跑通：`create_codebuddy_session`（`codebuddy_command="docker"`，args 内含
  `bash -c 'exec agy_acp_server'` 吞掉追加参数，`auth_method_id="oauth-personal"`）→ 返回
  `model_id=gemini-3.7-flash-high`、`model_name="Gemini 3.7 Flash (High)"`；
  `prompt_codebuddy "hi"` → `"Hello! How can I help you today?"`。
- **限制**：`switch_codebuddy_model` 对 agy 不可用 —— 桥接只发 `session/set_model`，agy 回 `{}`，
  桥接的 effective-model 校验直接报 `CodeBuddy did not return the effective model`。
  要支持需给 `AcpClient.set_model` 加 `session/set_config_option` 回退分支。
- 新增文件：`examples/docker_agy_hi.py`（自动生成补 nobody 组的 /etc/group + 注入 ANTIGRAVITY_HARNESS_PATH）。
- 补组补充实测（agent-harness:3，需 `--user root`，容器默认用户 master 无权限改 /etc/group）：
  `groupadd -r nobody` → `nobody:x:999:`；`groupadd nobody` → `nobody:x:1002:`。
  groupadd 存在于镜像（passwd 包）；/etc/login.defs 只有 GID_MIN=1000/GID_MAX=60000，
  无 SYS_GID_*，shadow 走内置默认（101..999）。该组的 gid 具体值无关紧要，只要名字查得到。
